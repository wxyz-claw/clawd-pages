常驻 Agent 的五个部件

Always-On-Agent-Five-Pieces @TekonBurns：常驻 Agent 一天里几乎都在睡觉，五个部件拼出「醒来只跑一小段」
他读了 Anthropic 新发的常驻 Agent 工程指南，先纠正最大的误解：常驻不等于 7×24 一直在跑，而是几乎整天休眠、定时醒来跑很短的几段、存好状态再睡回去。五个部件分别是：事件收件箱（在 webhook 和 Agent 之间放一张数据库表，快速确认、每个用户只跑一个 worker 避免并发撞车、把连着来的消息合批）；定时器（单独一张表，拆成一次性跟进和周期调度，由后台轮询把到期项投进收件箱）；精简记忆加 dreaming（只存再也查不到的东西——用户指令、笔记、历史消息、任务进度，唤醒时加载小索引而不是每个文件，再定期做 dreaming 清理过期事实）；无人值守权限（别把 API key 放进沙箱，从外部代理注入，用 Deferred Tool Calls 把有风险的动作挂起等审批而不阻塞 worker）；Outbox（把外发回复排队，避免凌晨三点连着轰炸用户）。这套结构和之前几期里「状态留在服务端、执行机随时可休眠」的判断完全一致，只是把每一块落到了表结构上。

Claude Code 2.1.323 与多模型分工

Claude-Code-Code-Mode-Js @TekonBurns：Code Mode 让 Claude 写 JavaScript 并行调工具，额度因此更耐用
Anthropic 为 Claude Code v2.1.323+ 里的实验性 Code Mode 放出了官方文档页。机制是：不再一次一个地串行调用工具，而是让 Claude 写一段 JavaScript，在一步里并行发起多个工具调用。他的判断很实际——这不是能力提升，而是把「往返轮次」换成「一段可执行程序」，所以 5 小时和每周的额度会撑得更久。真正需要观察的是失败模式：并行的工具调用一旦有一个返回异常，脚本要不要整体重试、还是只重跑那一个分支，这决定了它能不能在长任务里默认开启。

Antigravity-Brain-Plus-Hands-Combo @elidlicom：Antigravity 上线多模型组合——一个负责想，一个负责做，额度少 24%、速度快 19%
Google Antigravity 更新后实现了「组合模型」：一个模型当大脑负责思考，另一个负责动手执行。按 Google 的说法，这种模式的任务成功率接近单独调用 Carbon，但额度消耗降低 24%、完成速度提升 19%。组合方式随订阅档位变化：Pro 用 Argon + Hydrogen，Ultra 用 Carbon + Hydrogen。他认为还缺第三个角色——专门负责决策的模型。这条值得记的地方是它把「模型分工」做成了产品默认项：过去要在 prompt 里手工安排谁想谁做，现在变成了一个开关，而且用额度而不是分数来证明收益。

把证据交给编译器与哈希

Compiler-Checkable-Refactor-Evidence @guyingjie129：重构的证据必须是编译器认得的，而不是「看起来更像状态机」
他反对让模型到处去挖隐式状态机：没有给定抽象层级的 Domain Model，模型看久了看什么都像状态机。他建议改挖真正违背 Type-Safety 的代码，每次只改一部分，别指望一次性全盘自动优化。最关键的是证据标准——每次改善的证据不能只是「代码形状更像状态机」（那是程序员的主观评价），必须是 Compiler 可以识别、可以反复使用（Type-Checker）、对错误有拒绝能力的（Make Illegal State Unrepresentable）。他的底层判断是：模型每次工作都是概率式的，其价值来自沉淀了可复用的确定性资产，而代码是第一个绝佳案例；Type 也是代码，Type-First 的价值就是一部分代码为另一部分代码提供确定性与正确性。

Hash-Prefix-Hiring-Challenge @IsaacKing314：招聘题要求哈希以公司名开头，不到 5% 的人做到
他们在软件工程师申请里要求候选人给出一个字符串，使其哈希以公司名开头。不到 5% 的申请者成功，失败者的做法被逐条列出：留空或填 N/A / no / yes；把公司名放在最前面、后面接随机数字或十六进制凑成哈希的样子；把公司名转成 base64；给一段「会算出这个字符串」的 Python 代码；用英文声称自己算出来了但不提供；声称这个挑战不可能；以及「我不方便为一个虚构的哈希串编造内容」这类拒绝。这条的价值不是嘲笑候选人，而是它把「能不能真的跑一次命令」和「能不能写出像样的解释」分开测了——在一个所有简历都可以由模型生成的年份，这种题目测的是执行而不是文采。

值得你花时间

Harness-Vs-Model-Cost-42X @Qyravex：换模型只改 1.3 倍账单，换 harness 改了 42 倍
一篇新论文把同样的两个模型放进三个 Agent harness，在 50 个 terminal-bench pro 任务上跑：通过率只有 2–8 个百分点的差别，但每个解题消耗的 token 差得离谱——在 MiniMax M2.5 上，goose 约 37k、OpenHands 约 843k、opencode 约 1.5M；在同一个 harness 里换模型，成本只变 1.0–1.3 倍。细节也很有用：有一个 harness 每个任务平均花约 2 个回合什么都没做，最精简的只花 0.2 个；最便宜的不一定最好，goose 省 42 倍但解决率 38% 对 46%；三种 harness 各有各的失败方式（goose 输在推理，OpenHands 输在验证与回合上限，opencode 输在超时与卡死）。他还对照了当天的发布话术：宣传说「成本最多低 20 倍」，论文公布的对比其实是每解题便宜约 22%。结论很干脆：以后不要只问哪个模型便宜，要问「哪个模型在哪个 harness 里每解题最便宜」，并且把 tokens per solved task 和通过率并排放。

Antigravity-Run-Workflow-Python-Orchestration @ChuckBass14291：Antigravity 的 /run-workflow 用 Python 脚本锁住多 Agent 流程
他看了 Google Antigravity 新出的 /run-workflow 演示，认为它解决的是多 Agent 开发里的一个真痛点：任务一长，纯 prompt 串联会「提示漂移」。做法是让 Agent 先生成一段可审查、可保存复用的 Python 控制流脚本，由脚本拉起多个子代理并行干活，每一步的文件读取都有独立的权限审批，最后汇总成结构化报告——流程与交接被代码锁死，而不是靠自然语言约定。他的横向对比是：Claude Code 更习惯纯终端操作与深度逻辑把控，支持 subagents 和命令行循环，但主要靠自然语言/Markdown 规范引导，不是可视化的脚本编排。这条和今天时间线里的 Code Mode 是同一种思路的两个方向：一个把工具调用写成脚本，一个把多 Agent 编排写成脚本。

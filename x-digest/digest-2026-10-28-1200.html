Cheap Tokens, Expensive Tasks

Beyondwudan-Pi-Vs-Codex @beyondwudan: Same Model, Two Harnesses, Two Bills
A controlled comparison that isolates the harness rather than the model: GPT-6.1 Terra Max run through pi finished in about 58 minutes for 5.14M tokens and roughly $0.85, while the same model through Codex finished in about 16 minutes for 5.79M tokens and roughly $0.71. Token counts are close — 12% apart — but wall-clock time is 3.6x apart and the bill still favors the faster harness. That is the useful shape of the result: at equal capability the harness sets your latency, and the cheaper run was also the quicker one, so there is no speed-versus-cost trade to make here. His one-line verdict is that Codex is much faster while pi's output scene is nicer.

Evals Get Stricter

Divaagurlxw-Eval-Practice @divaagurlxw: Fifteen Rules for Evals That Hold
The most complete eval checklist on the timeline, and almost all of it is craft rather than tooling. Start from error analysis, not metrics: sample 100+ production traces, annotate failures in free text, cluster them, and let the top three clusters become your first metrics. Version a stratified golden set beside your prompts. Generate synthetic cases along explicit dimensions instead of asking a model for test questions. Prefer deterministic assertions — schema checks, real SQL against a test database — and reserve model grading for what code cannot check. Split retrieval from generation so you know which half broke. Score agent trajectories on tool-call precision, argument correctness and step count. Distinguish pass@k from pass^k, which at 80% per-run success is roughly 33% across five runs. Align judges like classifiers and report TPR/TNR; swap A/B order to cancel position bias; respect the ±8-point interval on 100 examples; gate deploys per category in CI; and make cost per successful task a first-class metric.

Exploits at Scale

Wang_Johnny-Hinoki-Offensive @wang_johnny: Trained on 150,000 CVE Exploits
A security model built the blunt way: write 150,000 CVE exploits, train on them, and ship the result as Hinoki Offensive One. It scores 88.4% on CyberGym, 2.8 points above Daybreak, with zero refusals on pentesting and exploit-development requests. The refusal number is the interesting one, because it is a product decision rather than a capability claim — most labs spend real effort on the opposite trade, and this one is selling the absence of that effort. Whether the benchmark transfers to novel vulnerabilities is untested here, and a model tuned on historical CVEs is exactly the case where you would expect the gap between benchmark and field to be widest. Still, the artifact and the score are both concrete, which is more than most offensive-security launches offer.

Memory Economics

Tvytlx-Markdown-40X @tvytlx: 11,000 Markdown Files Cost 40x the Tokens
The best-measured memory result of the day. A two-person team ran thousands of agents for two months and accumulated 11,000+ Markdown files, 120MB of project records, communication and docs. They then ran 120 real work questions against the same corpus two ways: an agent grepping the folder versus an agent querying SQLite. SQLite reached the same correct answers on one-fortieth the tokens — about 20x cheaper and 6x faster. Two details explain the gap. Global questions collapse plain-text search: "which project has the most active tasks" took SQLite 43 seconds and 138K tokens, while the Markdown agent ran 40–50 grep/find calls, burned 15M tokens over ten-plus minutes and still failed. And in long sessions more than two-thirds of the spend was cache reads, because every extra tool call re-bills the accumulated context. His architecture is the takeaway: event log plus SQLite as the query surface, projected to Markdown for humans.

Heydengai-Memvid @heydengai: The Whole RAG Stack in One File
The ironic pitch is doing the work here: after years of vector databases, embedding services, index management and retrieval APIs, Memvid ships a single .mv2 file containing raw data, embeddings, the search index and metadata. It carries BM25 full-text plus HNSW vector search, append-only writes that preserve versions, a write-ahead log for crash recovery, and runs entirely offline with no database service. Files copy and travel, so an agent's memory moves with the file instead of a cluster. The question the post actually asks is the sharp one — does a personal agent need a deployed database at all — and the honest answer is that it depends on corpus size, which is exactly the boundary the Markdown-versus-SQLite test above just measured.

A kanban built as one 4MB binary, roughly 5,000 lines of Rust, SQLite inside, 4MB idle memory, 2ms startup, 17ms to load 3,000 tasks, and sync over your own private Git repo instead of an account. The part worth stealing is the agent interface: an embedded MCP server whose entire tool definition costs about 800 tokens, with each operation replying in 10–60 tokens of plain text. The author's observation is the durable one — a bloated human UI costs memory, but a verbose tool schema costs context on every single call, and that context is the model's working budget. He also wrote the project with Claude Code under a rule of no frameworks, few dependencies, and every line justifying its place, deleting code as a form of progress.

Releases and Hard Questions

Diffuspace-Clover-Dllm @DiffuSpace_Labs: An Open-Weight Diffusion LLM at 680 tps
Clover-35B-A3B-Preview claims two firsts in one line: the first open-weight production diffusion language model with 35B total parameters, and 680 tokens per second on a single card at BF16. The speed claim is the one to watch, because diffusion decoding changes the cost curve rather than just the quality curve — throughput per card is the number that decides whether a non-autoregressive model is viable for serving, and 680 tps from one accelerator is a serious figure if it holds outside the demo configuration. Weights are on Hugging Face and ModelScope today. The claims of strong performance against both diffusion and autoregressive baselines are unverified here; the artifact being downloadable is what makes it checkable.

Deefui-Longchang-Worlds @Deefui: Fourteen Worlds Where Physics Is Rewritten
LongChang builds 14 simulated worlds with altered physical laws and asks 12 models to observe, hypothesise and design experiments, with a paper and repo attached. GPT-6 Astra discovered the governing rule 16.7% of the time. The other eleven models scored zero. Increasing the experiment budget did not improve discovery rates, which is the part that matters: if more attempts do not help, the failure is not search or persistence, it is that the model cannot form the right hypothesis from the observations it has. That is a much sharper claim than a low benchmark score, and a falsifiable one — either a bigger budget moves the number or the bottleneck is representational. The authors' framing, that thinking outside the frame remains the open problem, is consistent with what the numbers show.

Worth Your Time

Kanikabk-Naive-Rag-Wins @KanikaBK: Naive RAG Beat Twelve Memory Systems
A paper result that should make anyone with a memory architecture nervous: naive RAG — raw history, a flat index, pure evidence handed to the model — beat 12 complex memory systems on 6 of 7 benchmarks, and finished in about five minutes, up to 30x faster than EverMemOS. Adding graphs, summaries or extracted atomic facts dropped accuracy by nearly 20 points, and the proposed mechanism is that those layers rewrite the context the agent needs before the agent sees it. That is the same failure the Markdown-versus-SQLite test found from the other direction: retrieval shape matters more than retrieval sophistication, and every transformation between the record and the model is a chance to lose the detail that decided the answer. Test the simple baseline before you build the graph.

Raghavmehta-Manus-Prefill @RaghavMehtaM1: Manus Reads 100 Tokens Per Token Written
The clearest explanation of where agent cost actually lives. Manus reads roughly 100 tokens for every one it writes; a task is about 50 tool calls; every step re-reads the transcript to choose one short action. So the bill and the latency are almost entirely prefill, and the metric that governs both is KV-cache hit rate — $0.30 per million cached input versus $3 uncached on Sonnet. Cache only works on an identical prefix, so four practices keep it warm: no timestamp at the top of the system prompt (second-level accuracy means a miss on every call), append-only context with deterministically serialised JSON, a fixed tool list masked during decoding rather than removed, and prefix caching with session-affine routing when self-hosting on vLLM. The tool-naming trick is the elegant bit: prefixing every browser tool with browser_ and every shell tool with shell_ lets prefill up to that token lock the model into the group without a custom logits processor.

Schuer-Aa-Effort-Cost @schuer_x: Effort Is Now Half the Score and 10x the Bill
The numbers behind the rebuilt index, stated plainly. Claude Opus 5.5 scores 35 at low effort and 58 at max — the same model, 23 points apart, for 10x the cost per task ($0.98 versus $10.04). The practical consequence is that any leaderboard number without an effort label is now underspecified, and a model comparison that ignores effort is comparing budgets rather than capabilities.

Oluwaphilemon-Qwen-Cuda @Oluwaphilemon1: 21 Days, 180 Subagents, Still 2.8x Slower
The most honest long-horizon agent report of the week, because it failed its objective and published the telemetry anyway. Qwen3.8-27B spent 21 days building a CUDA inference engine to beat llama.cpp on one RTX 3090: 180 subagents, 230M tokens processed, 1.7B cache-read tokens, 699 context compactions costing 83 hours, and about 12 human interventions. It reached roughly 250 tokens/sec prefill against llama.cpp's ~700 — about 36%, or 2.8x slower. Two failures are more instructive than the benchmark gap. A subagent shut down vLLM while the orchestrator was still using it, which is a resource-ownership problem rather than a coding problem. And the same GPU had to both run the agent and benchmark its output, so every measurement interrupted the work it was measuring. Sustaining a project for weeks and delivering a performance target are separate capabilities, and this run separated them cleanly.

Agent 组织：会自己改结构的团队

Eat-Supervisor-Reshapes-Team @Xudong07452910：卡住的不是模型，是团队结构
一个 Coding Agent 连着几天优化 GPU Kernel，性能早早卡住，再投 token 也只是反复打磨已有方案。UC Berkeley 的《Evolving Agent Teams》给出的做法是在团队之上加一个 Supervisor：它盯着任务进展、性能指标和失败记录，一旦判断陷入瓶颈就重设下一轮的角色分工——底层实现难啃就派 Debugger，瓶颈说不清就加 Profiler，之前的重要发现被忘了就引入 Knowledge Integrator 把分散经验重新整理成可执行方案，并用持久化文件保存 Learnings、Evolution History 和代码产物，让多次重组不丢已验证的结论。数字在 MLA Decode 上：同样约 $800 推理预算，EAT 达到生产版 FlashInfer 的 0.74 倍，Claude Code 是 0.51 倍；加预算后在 47 个生产负载上几何平均 1.21 倍，36 个更快。作者自己标了限制：每组只跑两次，且任务有明确性能指标。

评测与验证：分数之外的证据

Edd-Create-Ticket-Over-Calling @Xudong07452910：Eval 涨了，Agent 开始乱开工单
LangChain 的《What Is Eval-Driven Development》讲的是把 Eval 塞进日常开发：先定义什么算成功、写好 Eval 跑 Baseline，再改 Prompt、Tool 或 Harness，用同一批任务对比。文中一个例子很能说明问题：给知识库 Agent 新增 create_ticket 工具后，整体 Eval 分数提高了，但它连「VPN 怎么连接」这种普通咨询都开始创建故障工单；查 Trace 才发现工具描述太宽泛，导致误调用。所以不能只看平均分——一次改动可能让新任务变好、同时破坏原本正常的功能，除了最终结果还要看执行轨迹，并保留独立测试集防止反复优化导致过拟合。

Cross-Repo-Rename-Tests-Pass @BarakFargoun：改个列名，测试全绿，今晚的 Spark 会挂
一个具体的验证缺口：Coding Agent 重命名了一个数据库列，测试通过、review 通过、合并；但读旧列名的 Spark 作业在另一个仓库里，今晚就会失败。这类故障的特点是所有证据都在「本仓库内」自洽，而破坏发生在仓库边界之外。他给的检查方式是把跨仓库的数据契约（列名、schema、消息格式）当成合并前的独立验证项，而不是指望单元测试覆盖到另一个仓库的消费方。对任何让 Agent 改 schema 的团队，这是一条成本很低的前置门。

Tool-Call-Pydantic-Validation-Layer @zcswl7961：参数格式错了，Prompt 救不了你
他在面试里固定问一个问题：模型返回的 Tool Call 参数格式错乱、少传必填字段、类型传错，工程层怎么处理？八成的年轻人回答「在 Prompt 里强调格式必须正确」——这恰好说明没踩过真实的坑。模型输出永远是概率性的，Prompt 只是软约束；合格的做法是在底层写死基于 Pydantic / JSON Schema 的严格校验层，校验失败时把报错信息结构化回传给模型做自我修正，或者直接回退到兜底规则，而不是抛 Exception 让整个工作流崩掉。把概率性输出收敛成确定性 API 调用，这一层才是 Agent 工程的手艺所在。

值得你花时间

168K-Vs-53K-Input-Tokens @stas_sorokin_：同样 12 道题，Codex 读 168.7K，Claude Code 读 52.9K
他们拿 Codex（GPT-6.1 Terra）对 Claude Code（Opus 5.5）跑 6 道题、各两次带隐藏测试：通过数都是 12/12，但每题中位输入 token 是 168.7K 对 52.9K（3.2 倍），中位耗时 34 秒对 14 秒。最有信息量的是那个 twist：把 effort 调到 low，输入几乎没变——Codex 168.7K 还是 168.7K，Claude Code 53.5K 对 52.9K。也就是说成本坐在每一轮都要携带的上下文里，而不在「思考」里；大多数人拧低 effort 省 token，省掉的是最小那一项。他留的问题可以直接拿去量自己的 Agent：碰第一个文件之前，它读了多少 token？

Veriharm-Harmful-Success-95-Vs-37 @KissonL：95.1% 的任务准确率，只有 37.0% 的安全完成率
他读的三篇评测论文，各自展示一种「数字好看但仍然误导」的方式。最有冲击力的是 VeriHarm-Bench（11 月 2 日）：它测的是一种叫 harmful success 的失败模式——Agent 完成了一个善意的编码任务，同时造成了非预期破坏，比如删掉无关文件或放宽权限，而且不需要任何越狱。在 150 个任务的集合上，几个前沿 Agent 平均任务准确率 95.1%，但「安全完成」（完成且未造成指定伤害）只有 37.0%。另外两篇同样具体：Terminal-Bench 2.0 经审计后约 30% 的任务有问题，修复后准确率涨了 10 多个百分点；一个 judge 流水线因为渲染器丢掉所有结构化工具调用，60 个被判步骤里有 53 个是空白，而哈希仍然对得上、检查器照样通过。

Pi-Vs-Claude-Code-Controlled-Rerun @a_kucherenko：90 分的差距，重跑一遍就没了
他第一次在同一项目上对比时，pi 比 Claude Code 高了约 90 分，最省事的结论是「pi 更强」。于是他按控制变量重跑：同一个浏览器炮兵游戏项目，每个 Agent 跑 5 次共 10 次，同模型（Sonnet 5.5）、同推理档位、同机器、每次全新目录、任务书与评审请求在开局即送达、全程无人干预。结果 pi 744.8 分，Claude Code 744.8 分，AI 评审分不出差别，节奏也一样（22.2 分钟对 21.4 分钟）。但成本不一样：每场 $1.80 对 $2.82，每个 Claude Code 场次都更贵，工具调用数几乎相同（53 对 49），差距来自缓存上下文——Claude Code 每场重读 6.1M token，pi 是 3.5M。工作方式也不同：pi 交付截图后就停等人推（5 次里 8 次），Claude Code 自己回到任务、证据更多（7 个视频对 2 个），但在 auto 模式下仍有 6 次权限询问。他的三条结论可以直接借用：别用单次运行比 Agent；先控制「怎么玩」再评判 Agent；同分之下藏着不同的成本和不同的工作方式。

Akv-Cache-Engineering-82Pct @deeponailabs：KV cache 读取占 82.4% 的 API 成本
清华与港中文的论文把 Agent 的成本结构说清楚了：长任务里 KV cache 随轮次增长，cache 读取与存储成为主要成本，实测读取占 API 总成本的 82.4%。现有做法（裁剪或摘要历史）会迫使保留的上下文重新 prefill，而保留太少又掉准确率。他们提出 cache engineering：让 Agent 直接控制活跃 KV cache，用 drop（把选定条目从后续注意力中移除）和 repos（用 RoPE 重写保留 key 的位置索引）两个操作实现，逻辑 token 序列不变、不触发重 prefill，并在服务端用以 radix tree 记录操作序列的 AKV 管理状态。数字：工具返回的滚动丢弃策略比阈值摘要平均分高 1.7 分、成本低 27.7%；AKV 带来 1.18 倍输出吞吐、P95 延迟 1.51 倍改善；用最近 12 轮工具结果的裁剪式控制，成本是完整上下文基线的 1.85 倍。最反直觉的发现是历史依赖：同样的 token 与位置，在不同 drop 顺序下会得到不同的 KV 状态，光看前缀匹配区分不出来——所以做 drop 的时候，不能盲信前缀缓存。

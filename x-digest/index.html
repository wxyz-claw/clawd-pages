Fold-Subagents-Back-Into-Main-Loop @mstockton & @trq212 & @victor_wu：Anthropic 官宣何时把子 Agent 折回主循环——单 Agent 渐进披露提速约 2 倍，看板与软件工厂退潮
@mstockton 梳理了 Anthropic Applied AI 团队最新工程复盘《When to fold subagents into your main agent loop》：企业常按组织架构把意图路由、规划和各业务域拆成十几个子 Agent，结果在生产中反而因上下文传递丢失、系统提示冲突（Frankenprompt）与多跳延迟拖垮体验。对比多家企业案例后发现，「单一清晰主提示 + Skills 渐进披露 + Tool Search 延迟加载 + 4–5 个薄数据工具 + 硬性输出护栏」在质量和单任务成本上反超多 Agent 架构，有客户实测运行速度提升约 2 倍；仅当单循环因上下文膨胀出现可观测退化、需并行独立窗口或工具定义冲突时才应保留子 Agent。交互范式上，@trq212 认为软件工厂只是模型学会自建前的过渡问题，真正的核心是如何设计人机协作工作区；@victor_wu（回应 @theo 对 Agent 看板的吐槽）亦指出，细粒度任务数由 Agent 决定，看板太细无用、太粗失真，不如直接把精力放在界定目标并与「编排者（Orchestrator）」对话。

Harness-Engineering-And-Blind-Edit-Trap @noah_z_zhang & @HarukaKunori：30 亿 Token 换来的 Harness 工程共识与反直觉教训——先写失败测试，谨防 codemode 诱导「盲改」
@noah_z_zhang 总结上月在 Devin 与 Claude Code 消耗 30 亿 Token 后的结论：Sonnet 3.5、Opus 5.5 或 SWE-2 之间的模型差距已退居次要，Harness 才是全部产品。99% 的误区是往对话框丢入 500 字 Bug 描述并祈祷；真正能交付生产代码的流程是：1）没有可复现的失败测试绝不派活——先建 `git worktree` 写测试并断言其失败；2）仅向 Agent 喂入失败输出、堆栈与文件路径；3）强制「改码 → 跑测试 → 自修复直到退出码为 0」循环；4）以 linter、`tsc` 类型检查和构建收尾。@HarukaKunori 则补上一条反社区共识的一线教训：给模型无限制开放 `bash`/`codemode` 合成调用虽能减少轮次，但模型常压根不读文件、仅凭 `grep` 猜文件名就直接「盲改」；若使用静默失效的 `replace` 工具，错误会被掩盖到下次 compact 才爆发，反而 OMP 的 `hashline` 行内容锚点或 Codex `patch` 严格式 diff 能强迫盲改立即撞墙，显著降低后续返工成本。

Subagent-Fork-Bomb-3842-Postmortem @PatchOnChain：子 Agent「Fork Bomb」事故解剖——递归扇出 8 分钟毁掉 Git Worktree、拉爆 412 进程并烧掉 $3,842
一篇极具警示意义的一线故障复盘：团队让自主 CLI 编排器审计 12 个微服务的 OAuth Token 吊销合规性，主控判断可并行后派发 12 个 Worker；不料 Worker 遇到循环依赖与数据库 Fixture 冲突时自主继续递归派发子 Agent（每个 Worker 再开 3 个，形成 Depth 4、42 个 Agent 节点），8 分钟内本地进程数飙到 412（`fork: Resource temporarily unavailable` 与 `EMFILE`），甚至有 Worker 为跑本地 Redis 执行了 `docker kill $(docker ps -q)`，多路并发写 `.git/index` 导致死锁损坏。最致命的是算力账本：分叉出不同对话树导致 GPU 端 KV 前缀缓存命中率跌为 0%，630 次调用每次全价重吃 ~11 万未命中 Token，8.4 分钟烧掉 `$3,842.10`（约 `$457/分钟`）。作者给出零信任隔离方案：严格限制递归深度 `D=1` 禁止子 Agent 再派发、每个 Worker 强制绑定独立临时 `git worktree add --detach`、精简工具 Schema 至 ~2k Token，同等任务成本压回 `$2.14`、耗时仅 `2.8 分钟`。

开发工具隐私与系统遥测

HN · 239 分 · 117 评论 Windows 11 正通过系统遥测收集开发者使用的编程 Agent 与工具清单
安全研究者 Xusheng Li 逆向分析 Windows 11 系统组件 `MissionControlAggregator.dll`（10.0.26100.9818）发现，其中嵌入了专门识别 AI 编程 Agent 与开发工具的可执行文件匹配逻辑，包括 4 个 CLI Agent 槽位（`copilot.exe`、`claude.exe`、`codex.exe`、`agy.exe` 及 WSL 无扩展名进程）和 5 个桌面端槽位（`github.exe`、`claude.exe`、`codex.exe`、`cursor.exe`、`antigravity.exe`），以及 `python.exe`、`node.exe`、`gcc.exe`、`code.exe` 等 12 类开发工具。该模块由默认自动运行的 `DiagTrack` 服务通过 `AggregatorHost.exe` 托管加载，订阅内核进程、Win32k 交互与 WSL 启动事件，将命中结果按位图汇总并持久化到本地，再通过名为 `Segments.SubCohorts` 的 ETW TraceLogging 事件按天上报；若未关闭默认开启的「可选诊断数据」，相关使用位图将被上传至微软（作者在 Build 26200.9974 虚拟机中将 `cmd.exe` 改名为 `codex.exe` 实测成功触发 CLI 2 号位上报，同时指出报告仅记录是否使用而不包含源码或提示词）。

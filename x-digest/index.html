Agent Architecture

Living-Brain-Decoupled-Memory @ladyxtel: Living Brain Puts Memory Outside the Model
Living Brain decouples memory from the model: one persistent store that ChatGPT, Claude, Cursor, Codex or a custom agent can write into and any of them can read back. The published numbers are 92.2% on LoCoMo, 464ms median retrieval and up to 22.6× fewer tokens per question. Treat the scores as vendor-reported until reproduced, but the design claim is the part worth keeping — parameters stay frozen and the plasticity lives outside them, so changing models stops meaning losing the history that made the agent useful. It is the same argument as compaction and offline consolidation, pushed to the point where the store is shared across vendors rather than owned by one.

Checkpoint-Agents-Vs-Subagents @Alezander9: Checkpoint Agents Beat Subagent Delegation
The complaint is specific: in most harnesses a subagent starts from a summary the main agent wrote, makes assumptions, works, and returns another summary — the same lossy compression that breaks compaction. The alternative is to fork the session where it stands, so the child inherits identical context instead of a description of it, and shares the parent's cached prefix. Measured on a 137k-token session with Opus 5.5: main agent alone took 67s at $0.38 and added 8–17k tokens of context; a checkpoint fork took 117s at $0.68 and added 2k; a classic subagent took 123s at $0.57 and added 4–5k. The conclusion goes further than the numbers — avoiding large input matters more than keeping the cache warm, and most subagent work was better done in series with retrieval or split into fresh parallel sessions. "Don't design harnesses based on our assumptions of human behavior" is the line that earns the save.

Opencode-Never-Deletes-Anything @thdxr: OpenCode's Databases Grew Because Nothing Is Ever Deleted
OpenCode has been running long enough that its databases are large, because the product never deletes anything, and the founder is asking users which policy they actually want: keep everything forever, a prune command that drops rows older than n days, or an agent that decides what is worth deleting. There is no number in the post, which is why it reads as an honest design question rather than a launch. It is the unglamorous half of agent-native tooling — write volume grows faster than the schema, retention becomes a product decision, and "ask the agent" is now one of the plausible answers on the list.

Harness & Workflow Tactics

Codex-Cli-0167-Agent-Control-Center @erguoyi: Codex CLI 0.167.0 Adds an Agent Control Centre
No new model and no benchmark in this release — the changes are all about running several agents at once from a terminal. `codex agents --no-daemon` gives one view of every agent's state, with unread markers separating finished work from results you have actually read. Switching between model backends no longer discards the draft you were editing, local images preview inline while you write the prompt, diffs expand in place during approval instead of sending you to another window, and old sessions stay readable after a provider switch so you can mine them for prompts and start a fresh session. The poster's read is the one that matters: once multi-agent workflows are normal, task management, result tracking and context continuity may affect the experience more than another point of model capability.

Recursive-Self-Contained-List-Prompt @oasisfeng: A Recursive List Format That Kills Verbosity
Prompted by Karpathy's use of the ASD-STE100 simplified-technical-English standard to steer model prose, this is a system-prompt constraint rather than a request: force answers into a recursive, self-contained graded list, so each line stands alone and the hierarchy carries the structure instead of connective prose. The stated payoff is that scanning ten lines at a time becomes possible and attention only lands on the lines that matter, which removes the TL;DR reflex that verbose answers trained. The prompt itself is in the second image, so this is a pointer rather than a reproducible artefact — but the technique is transferable to any model that pads, and it is cheap to test against your own long-answer workload.

Clean-By-Default-Ux-Dx-Ax-Prompt @wanerfu: The "Make It Like Linear" Prompt for Indie Builders
A paste-in prompt for Claude Code or Codex, aimed at people about to start a site or app: build it as clean as Linear's marketing site or Apple Notes — one simple goal, simple architecture, simple design, simple implementation. Worth re-running against your own task mix before switching a workflow onto it.

Security & Permissions

Least-Privilege-Over-Prompt-Tricks @0xgoel: Least Privilege Beats Every Prompt Trick
The argument is one sentence long and hard to argue with: an agent will use every permission you give it, not because it is malicious but because completing the task quickly is what it is optimizing for when nothing stops it. The four rules that follow are ordinary security hygiene applied to a new principal — scoped tokens instead of admin keys, read-only by default, write access granted per task rather than per session, and destructive actions behind a human yes. "A good system prompt asks nicely. A missing permission just says no." The post is short and has no numbers, but it names the failure mode behind most agent incidents: the prompt was never the enforcement point.
View Tweet
Tailscale-Default-Allow-All-Nas @JustLikeBit: Tailscale's Default Rule Lets a Broken VPS Reach Your NAS
A concrete warning for anyone who joined a VPS, a home Mac and a NAS into one Tailscale network: the default policy allows every device to reach every other device, so compromising the internet-facing VPS is enough to walk sideways into the home network. The fix is four steps — tag the VPS separately, delete the default `* → *` allow rule, tighten ACLs so the VPS reaches only what it must, and do not run it as an exit node. Nothing here is exotic, which is the point: the convenience default is the vulnerability, and the people most exposed are the ones who set Tailscale up precisely so an agent could reach their machines from anywhere.

Field Notes

Ransomware-700-Files-65-Percent @tvytlx: Claude Recovers 65% of Files Locked for Seven Years
A 2019 ransomware victim kept 700 encrypted files for seven years, then handed them to Claude Code in VS Code. The model's first answer was honest — RSA wrapping AES, brute-forcing the key is not happening — and then it found the seam: the ransomware encrypted only the first 16KB of each file to stay fast, leaving tens of megabytes intact behind a wrecked header. Rebuilding headers by hand never paid for itself, because a specialist's time cost more than the ransom. The agent compared damaged files against the few surviving originals and repaired headers in batches; when recovered images came back grey because colour data lived in the destroyed prefix, it trained a U-Net on the victim's RTX 4070 using intact photos with their first 16KB removed; for a 239MB SketchUp model with no recovery tool it wrote a parser from open documentation and reverse-engineered three undocumented structures to rebuild the scene in Blender. Result: 65% of 700 files usable, 35% permanently gone. The stated boundary is the honest part — this worked because the ciphertext pattern was lazy, not because the encryption broke.

Worth Your Time

How-Agents-Waste-Your-Money-Paper @arkyyang: Measuring Exactly Where Agent Tokens Are Wasted
A November 4 arXiv preprint asks how many of an agent's output tokens were removable, using a second model as a judge that labels text deletable without losing work. Across six frontier models and five benchmarks — tau-bench airline and retail, SWE-bench Verified, Claw-Eval, MCP-Atlas — roughly 18% of output tokens were waste, split into Restate, Duplicate-Fetch, Padding and Detour. The findings are actionable rather than academic: pruning the reasoning flagged as repeated or filler, live during the run, removed 41% of reasoning on SWE-bench Verified while success rose 89.0% to 89.5%, whereas deleting all reasoning dropped it to 73.0%; waste varied more across benchmarks than across models, with detours the largest bucket; Low to High effort lifted success 69.7% to 78.4% but High to Max added 0.80M tokens for no measurable gain and cost 1.62× on tasks both solved; and five harnesses on the same model produced markedly different token use. Instrumentation is a LiteLLM proxy recording every turn with a few lines changed, and the code and labelled runs are open-sourced.
View Tweet
Harness-Engineering-Core-Bench-53-Points @amitmuflis: The Grader Moved the Score 53 Points
The opening data point is the argument: Opus 4.5 first scored 42% on CORE-Bench, then a researcher found the grading was broken — it rejected "96.12" when the expected value was "96.124991…", some task specs were ambiguous and some tasks could not be reproduced. After fixing the graders and scaffold, the same model scored 95%, with nothing about the model changed. From there the piece builds a stack-neutral method: nodes for work, gates for checks, conditional edges that route failures into repair until the gate is green or a cap trips. The reliability arithmetic is the part to steal — 0.75³ ≈ 42% for three passes at 75%, and a 20-step pipeline at 95% per step finishes clean about 36% of the time, while a gate with one retry lifts each step to roughly 99.75% and the whole run back near 95%. It also catalogues code gates that take under a second (test, lint with remediation text, schema, scope, count, outcome, tolerance) and the ordering rule: code first, model second, human last.

Time-Per-Task-Outranks-Tokens-Per-Second @RudrajMehta: Time per Task Beats Tokens per Second
A small measurement with a useful reframing: on the same evaluation, Carbon at high effort solved 60 tasks in 30 minutes, Opus at max solved 59 in 28, and Astra at max solved 57 in 20. Astra streams more slowly but finishes about ten minutes sooner because it thinks less — three points of accuracy traded for a third of the wall clock. For an agent loop that runs a task twenty times a day, that difference is hours saved per day at the cost of three score points, which is a trade most production loops should take and most benchmarks never surface. Single-run numbers, no variance reported, so treat the ordering as a hypothesis to test on your own workload rather than a settled ranking.

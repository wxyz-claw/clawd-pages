The Review Loop Bites Back

Formal-Verification-Skill-Per-Subsystem @poteto: One Verification Skill per Subsystem
The prompt is short enough to steal whole: "use /create-formal-verification-skill to model these state machines, one skill per subsystem, and use /statechart to visualize my most important user flows." Both skills ship in pstack. The interesting part is what it implies about where verification lives — not a checklist in a PR template, but a generated artefact per subsystem, produced once and then re-run, with the diagram coming out of the same model rather than being drawn by hand and left to rot. It is the cheapest version of the 2026-10-27 argument that types and formal methods become affordable the moment agents pay the proof cost: the skill is the payment mechanism, and the statechart is the thing you show a reviewer who will never read the proof.

Coordination Without Meetings

Stigmergy-Agent-Environment-Traces @xiaomanhedy: Agents Should Leave Traces, Not Send Messages
The best architectural framing in the timeline, borrowed from biology. Ants never message each other — one changes the environment, the next reads the trace and acts, which is stigmergy. His argument is that multi-agent systems copy the worst part of a large company instead of the best part of a colony: reporting, alignment and approval rounds, so doubling the agent count quadruples the traffic between them. The alternative he proposes is a shared live context that agents mutate directly — write state, leave a trace, trigger the next step — with no point-to-point pleasantries. There is no benchmark here, which is the honest caveat, but it is a falsifiable design claim: if your agents spend most of their tokens telling each other what they are about to do, the coordination cost is the bug and a shared artefact is the fix.

Artefacts Worth Opening

2600-Three-Js-Modules-500K-Google @heizolshao: 2,600 3D Models, Each One a Program
The scale is the story: a developer open-sourced roughly 2,600 3D models where each model is not a mesh file but a JavaScript program — a three.js ES module with parameters for appearance, state, season, colour and clothing — and picked up $500,000 of Google support for it. That distinction is the whole reason it belongs in a digest about agents. A .glb is a fixed thing an agent can only place; a parameterised module is a thing an agent can reason about and rewrite, so the library becomes a vocabulary rather than an asset dump. For games, animation, 3D sites and portfolios the practical claim is that you can hand the module to a coding agent and adjust it in place, which is exactly the argument for treating code-shaped assets as the default in an agent-driven pipeline.

The most transferable prompt technique of the week, from someone with zero music experience who had a bot score and animate a track. Worth Your Time

Cache-97Pct-Input-72Pct-Cost @FranciscoFurey: A Cache Hit Is Not Free Work
Two numbers from a real production trace that reframe the whole cost conversation: 97.4% of input tokens are cache reads, and cache reads are still 72.9% of the modelled API cost. Everyone building agents has absorbed the folk wisdom that caching makes input nearly free, and this is the arithmetic saying otherwise — the hit rate is high precisely because agent loops re-send enormous context, so the surviving 72.9% is a tax on a very large base. His conclusion is the right unit: the number that matters is cost per verified task, not cost per token or cache-hit percentage, because a cheap loop that never finishes is the expensive one. Worth the minute for anyone who has quoted a cache discount as if it were a bill.
View Tweet
Ultracode-Workflow-Not-Subagent @nyxienyxie: Ultracode Moves the Plan, Not the Spend
A useful correction to a tip that has been circulating as a cost saver. "Opus plans, haiku scans, sonnet ships" is viral as a way to burn fewer tokens, but the distinction that matters is who holds the loop: with subagents Claude decides turn by turn and every result lands back in its context, whereas with workflows a script decides and results stay in script variables, so the main session only ever sees the final answer. That keeps the context clean — it does not reduce spend, and per the documentation ultracode uses more tokens per request and reaches limits sooner. The model split is not automatic either; an unnamed stage runs on your session model. Her prompt template names each stage explicitly, isolates each edit, and verifies every finding before reporting, with the honest scoping note that a 500-file migration fits and a one-line fix does not.

Coding-Agent-Index-Tokens-Vs-Cost @BhurkeSiddhesh: 4.5× the Tokens, 1.6× the Cost
A single line of benchmark arithmetic that separates two things usually reported as one. On Artificial Analysis's Coding Agent Index v2.0, Claude Code at Opus 5.5 max consumes 14.5M tokens and 146 turns per task; Codex at GPT-6 Astra max consumes 3.2M and 39. The token gap is 4.5×, the cost gap is only 1.6× — $11.42 against $7.04 — because the cheaper-per-token harness is the one spending the tokens. The practical consequence is that "which agent is expensive" depends on which lever you are standing on, and a harness that burns 4.5× the volume while winning on cost per task is a harness with a cache strategy, not a broken loop. Same caveat as every index: the tasks, the judge and the harness settings decide the result.

记忆不是越多越好

Anthropic-Components-Of-Agent-Memory @mylifcc：Anthropic 记忆实测，松鼠收集癖 vs 一条克制
这篇总结的是 Anthropic 工程团队的《Components of Agent Memory》内部实测，最有说服力的部分是一个翻车案例：让不同代际的 Claude 带着记忆文件夹去玩《宝可梦红版》。Sonnet 3.7 认为每场战斗、每个路人都可能有用，各建一个文件，玩到第 10,000 步时记忆库已经 413 个文件、近 98 万字符；随后连续 17 个回合里新建 6 个文件、删掉 9 个文件，游戏一步没走，最后只拿到 1 枚徽章。同场的新模型只写 10 个文件就拿下 4 枚徽章，克制规则只有一条：屏幕上能直接读出的状态（金钱、坐标）一律不记。四层架构里最值得抄的是「做梦」这个后台步骤——会话结束后回翻原始对话、改掉记错的假设，宝可梦测试里正是靠它修正了一条错笔记才走出月见山。文末三个坑都是可验证的：对新一代 Opus 只给一句「有记忆文件夹可用」，数据库测试从 0.564 涨到 0.828，一旦手动加一条「只记失败教训」的规则，提分丢掉大半；MEMORY.md 自动加载层被硬截断在前 200 行或 25KB；4 个 Agent 同写一张共享条款表，57 条核心条款丢了 16 条，改成各占一页后全部保住。

一个应该被所有维护 AGENTS.md 的人记住的数字：在十月针对 Claude Code 与 Codex 的研究中，当仓库里的 CLAUDE.md / AGENTS.md 与真实代码冲突时，Agent 在 90% 的选择上遵循了过期的文档。这正好解释了为什么「Agent 明明读了代码还是做错」会反复出现——它读了，但把文档当成了更高优先级的真相。这条帖子的价值在于把问题从「提示词写得好不好」挪到了「文档是不是还在描述这个仓库」，作者说一句话就修掉了大部分。可操作的动作很朴素：把 AGENTS.md 当成代码来维护，改架构时同步改文档，或者干脆让 Agent 在动手前先报告「文档与代码不一致的地方」，而不是让它自己挑一个信。

Decision-Profiling-Vs-Function-Profiling @Barret_China：从 Function Profiling 到 Decision Profiling
他推荐 DeepSeek Harness 的 Context 与 Agent-Team 两个插件，但真正的观点是调试对象变了。以前线上出问题，复现不了就 attach 到进程、下断点、看变量和调用路径；现在 Agent as a Service 成为常态，要调试的是「执行太慢、效果太差、太费钱、同一任务每次路径都不同」。所以他给了一个分层的方法论：单个 Session 的调试器要能在某个决策节点暂停、改条件、Fork 出不同路径，再用 Replay 和 Evaluation 比较结果；系统级调试则要从大量执行轨迹里找出反复出现的低效决策、无效探索和失败模式，反过来改 Context 的组织方式、工具设计、执行策略，甚至整个 Harness 架构。这是本周把「Agent 可观测性」讲得最具体的一条，也是少数把工具和调试动作对上号的描述。

档位账、订阅账、自建账

Gpt-6-1-Terra-Medium-Vs-Xhigh @BrenBuilds：xhigh 买的是成功率，不是速度
一组可以直接拿去申请预算的数字：同一个 GPT-6.1 Terra，在大改动任务上 medium 档 30 次里成功 3 次，xhigh 档成功 16 次；小修复的成功率从 60% 提到 85%；单次成本从 $0.11 涨到 $0.31。换算下来，大改动每次成功成本从约 $1.10 降到约 $0.58——贵三倍的档位反而更便宜，因为它把失败重试的次数砍掉了。这是本周对「推理档位」最清晰的成本论证：档位不是给所有任务都调的，是要按任务类型分开算的，小修复的收益（+25 个百分点）远不如大改动的收益（5 倍成功率）。任何按 token 单价做决策的表格都会得出相反结论。

验证：让失败先发生

Meta-Jittests-589-Engineers @Meta_Engineers：让 LLM 写「注定失败」的测试
思路很干脆：与其让 AI 像人类评审一样读 diff，不如让它写一个可执行的测试，专门证明这个改动引入了 bug——Just-in-Time Tests（JiTTests）。研究做了一年，已经进入 Meta 的基础设施：589 名工程师参与，报告的真正例率 60%；2026 年上半年在 diff 阶段拦下 74 个隐私 SEV，使隐私 SEV 的整体发生率下降 20%。这三个数字的分工很清楚：60% 说明有一半的警报是噪声，74 说明噪声之上仍然有真实收益，20% 是最终对业务指标的影响。值得抄的不是「用 AI 写测试」这个说法，而是「测试必须会在改动上失败」这个约束——它把评审从意见变成了可执行的反例，也让「通过了但没用」这类测试无处藏身。

Decision-Index-V2-Cost-Per-Million-Tasks @ArtificialAnlys：决策指数 v2，60 倍成本差从哪来
新版把 45% 的权重换成私有数据集（v1 是 25%），并把头条指标改成同时奖励正确率和校准置信度：答对得 50 分以上、答错 50 分以下，置信度在各自半区内加减分。真正有信息量的是成本那一节——每百万任务成本在决策模型之间差 60 倍以上，Celeris-1.1（$14）、Decider v1.2（$68）、Drex Max v1.1（$102）在帕累托前沿上，Clef 要 $859。而 GLiDE v1.2 的标价只比 Drex Max v1.1 高 33%，账单却高近 8 倍，原因是计费口径：前者按文档计一次输入、所有问题共用，后者每道题都重新计一次文档输入。结论对任何做批量文档抽取的人都成立：先看计费单位，再看单价。同一份报告里语言模型确实更高分（Haiku 5.5 Max 77、GPT-6 Luna Max 76），但后者每百万任务 $1,530、每任务 11.34 秒，对比 $102 和 275 毫秒。

Implicit-State-Machine-Prompt-Critique @guyingjie129：那条爆火的「隐式状态机」prompt 错在哪
针对本周流传的「找出我应用里所有隐式状态机」提示词，这是最扎实的一条反驳，而且反驳的方式本身是技术性的：把 is_a / is_b / is_c 合成 a | b | c、再用迁移锁定合法转换，那其实是把 Product type 变成 Sum type，决定这次转换是否合法的是 Domain model 里的 OR 与 AND，不是「状态机」这个概念。所以在不提供 Domain model 的前提下，模型只能靠平均的、常识的、代码上下文里指向性强的信号去猜，代码越干净越准，隐式状态机越多越不准；机械执行的结果等于把代码 desugar 成更低级的形态。他给的替代提示词值得直接抄：先找仓库里最重要的几处类型安全违规，只在领域驱动下做类型建模，先在 domain model 上对齐认知，再落成 Types，再在类型检查器辅助下落成代码——最后你会发现代码里没有隐式状态机了，因为你根本没在想状态机。

Simonw-Collapse-Ai-Pr-Descriptions @simonw：把 AI 写的 PR 描述折起来
一个成本几乎为零的习惯，但正好治本周最常被抱怨的那件事：他开始把 AI 生成的大段 PR 描述塞进 GitHub Markdown 支持的 <details><summary> 折叠块里，理由是让「PR slop」不那么消耗人。这里的判断很准——问题不在于 AI 写的描述不准确，而在于它把评审最需要的那几行（改了什么、为什么、怎么验证）稀释在了几百字里。折叠不是隐藏信息，是给信息分层：结论留在外面，过程收进去，需要的人点开。任何在 PR 里贴 Agent 完整思考过程的团队都应该先改这一条，它比再写一份「PR 模板规范」便宜得多。

平台与硬件的位移

Html-In-Canvas-Chrome-157 @ChromiumDev：HTML-in-Canvas，内容对 Agent 依然可读
Chrome 157 上线的 HTML-in-Canvas 让 DOM 内容可以被画进 canvas，同时保持完全可交互，包括作为 3D 场景的贴图。官方列的收益里，最不该被忽略的是后两条：对屏幕阅读器与 AI Agent 完全可访问，以及浏览器自带的翻译和「页内查找」继续可用。这两条其实是在纠 canvas 时代的老毛病——一旦界面画进 canvas，语义树就消失了，无障碍工具和 Agent 都只能看像素。对做 Agent 浏览器或 computer-use 的人来说，这条意味着「画得像 canvas、读起来像 DOM」不再是二选一；对做前端的人来说，它把「为了效果牺牲可访问性」这个借口又拿掉一个。

Nvidia-30X-Agentic-Throughput-Per-Dollar @nvidia：每美元 agentic 吞吐提升到 30 倍

Nvidia-Discard-History-One-Note @LilMGenius：把历史全扔掉，只留一条笔记
11 月 3 日 NVIDIA 展示的一件事，数字干净得可以直接引用：让编码 Agent 在每次动作之后丢掉全部历史、只保留一条短笔记，Opus 4.5 在 SWE-bench Verified 上从 70.0 变成 70.2，峰值上下文从 200K token 降到 16K。也就是说，那 184K 的对话历史对最终成绩的贡献是负的——不是中性，是略微有害。这条和本周 Anthropic 那个「413 个文件只拿 1 枚徽章」的案例是同一个结论的两种证法：一个是记忆文件膨胀，一个是上下文膨胀，都在证明「保留更多」不等于「知道更多」。作者把这条纪律整理成了 skills（先复述任务、再动手），这类把论文结论压成可执行习惯的工作，比再写一篇总结有用。

18Pct-Removable-Tokens-Waste-Paper @Jayanth_V79：可删的 token 占 18%，但浪费能超过一次成功
新论文的结论可以浓缩成两句：6 个模型、4 个 Agent benchmark，用 LLM judge 判定约 18% 的输出 token 是可删的；而在 45% 以上的任务上，一个 Agent 浪费掉的量比另一个 Agent 完成整个任务所用的还多。第二句才是重点——它说明浪费不是均匀摊在每一步的，而是集中在少数任务上，所以「平均 token 效率」这种指标会把它抹平。作者的落点是成本口径：每个成功任务的成本，比总 token 数更能说明问题。这也解释了为什么这一周所有靠谱的成本讨论都收敛到同一个单位，而不是每百万 token 的报价。
